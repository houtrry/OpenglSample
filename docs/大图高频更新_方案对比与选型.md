## 大图高频更新：方案对比与选型（ES 2.0 / RK3399・RK3588）

### 1. 概述与约束
- 目标：大地图（~20000×20000）在高频（~10Hz）更新场景下的稳定渲染与资源可控。
- 环境：OpenGL ES 2.0；Android RK3399 / RK3588。
- 关联文档：
  - `docs/超大纹理渲染_Tile方案.md`
  - `docs/Tile_LOD_方案设计.md`
  - `docs/Tile方案_高频更新再评估.md`

### 2. 方案清单与原理
- **A) Tile + LOD（金字塔）+ 脏区 + 子矩形上传（推荐，局部更新）**
  - 原理：将大图切成固定瓦片（建议 512），每帧仅对变更区域映射到相关瓦片的子矩形，用 `glTexSubImage2D` 局部上传；低层 LOD 兜底显示。
  - 关键：脏区合并、逐行 memcpy（NDK/NEON）、上传限速（MB/帧）。

- **B) 外部纹理链路（Camera/Video 式）`GL_OES_EGL_image_external`（推荐，整帧更新）**
  - 原理：生产者（相机 ISP、硬件解码器或视频式源）将帧写入 `GraphicBuffer`，GL 侧用 `samplerExternalOES` 采样，仅 `updateTexImage()`，几乎不做 CPU 拷贝。
  - 关键：YUV420 输入，片元做色彩转换；双/三缓冲；VSYNC 驱动。

- **C) Clipmap / Virtual Texture（环形缓冲）**
  - 原理：围绕相机维护分层环形纹理缓冲，移动时只更新进入的环形条带。
  - 特长：大范围平移更新量与“移动距离”相关，而非全图面积；与 A/B 可组合。

- **D) 硬件 mipmap（PoT+padding）**
  - 原理：瓦片为 2 的幂，`glGenerateMipmap` 生成 mip 链。
  - 限制：ES 2.0 对 NPOT+mipmap 受限；频繁更新重建整链，成本高。

- **E) ES 3.0+ PBO / 持久映射**
  - 原理：异步像素传输，降低 `TexSubImage2D` 卡顿。
  - 限制：本项目基线为 ES 2.0，仅可作为高端机兜底方向。

- **F) 压缩纹理（ETC1/ASTC）**
  - 原理：离线压缩降低带宽/显存。
  - 限制：高频在线更新实时压缩代价大，适合静态或低频层。

- **G) 程序性生成 / Shader 映射**
  - 原理：以参数驱动像素在片元生成；少上传多计算。
  - 限制：取决于业务能否以公式表达。

### 3. 对比维度（结论性摘要）
- **CPU 占用**：B（最低） < C/A（中） < D/F（中高） < 逐像素实现的 A（高）。
- **带宽压力**：B（YUV420 + 零拷贝低） < A/C（取决于脏区面积） < D/F（链重建/重传可能高）。
- **时延/稳定性**：B（稳定、流水线） ≈ A（限速后稳定） > 其他。
- **实现复杂度**：A（中）/B（中）/C（中高）/D（低中）/E（高）/F（中）/G（不定）。
- **平台依赖**：B 依赖 `GL_OES_EGL_image_external`；E 需 ES3+；F 依赖硬件格式支持。

### 4. 场景选型与最佳实践

#### 场景一：大地图高频更新 + 每帧全图更新
- **最佳方案**：优先采用 **B 外部纹理链路**；若源为自生成帧，改造成“视频式生产者”输出到 `Surface`。
- **原因**：整帧变动下，Tile 的逐瓦片上传将不可控；外部纹理链路避免 CPU 大拷贝，利用 ISP/VPU/HWC 管线。

```mermaid
flowchart TD
    SRC[生产者: 相机/硬解码器/视频式生成] --> GB[GraphicBuffer (gralloc)]
    GB --> BQ[BufferQueue/Surface]
    BQ --> ST[SurfaceTexture/EGLImage]
    ST --> GL[GL samplerExternalOES 渲染]
    GL --> OUT[显示/合成]
```

- **落地步骤（ES 2.0）**：
  1) 检查扩展：`GL_OES_EGL_image_external`、`EGL_ANDROID_image_native_buffer`。
  2) 创建 `external OES` 纹理与 `SurfaceTexture`，获取 `Surface`。
  3) 让生产者将 YUV420 帧写入 `Surface`（Camera/MediaCodec/自定义 pipeline）。
  4) 渲染线程每帧 `updateTexImage()`，片元用 `samplerExternalOES` 着色器做 YUV→RGB。
  5) 合成其他 UI/覆盖层；必要时开启三缓冲、限帧、降分辨率。
- **可选增强**：
  - 若必须 CPU 生成帧：尽量在后台线程生成，降低分辨率/帧率，或通过硬编→硬解形成硬件链路。
  - 超大分辨率（> 4K）仍需评估 HWC/GPU 合成能力，必要时分块显示或降采样。

#### 场景二：大地图高频更新 + 每帧局部更新
- **最佳方案**：采用 **A Tile + LOD + 脏区 + 子矩形上传**；必要时叠加 **C Clipmap**。
- **原因**：局部变化时，按瓦片子矩形上传能严格按需用带宽；LOD 可兜底视觉；Clipmap 对大范围平移最优。

```mermaid
flowchart TD
    In[脏区列表 Rect[]] --> M[合并/裁剪]
    M --> T[映射到瓦片 (tx,ty)]
    T --> S[求瓦片内 subRect]
    S --> Cpy[逐行 memcpy 到像素缓冲]
    Cpy --> U[GL: glTexSubImage2D(subRect)]
    U --> R[Renderer 批渲染 + LOD兜底]
```

- **落地步骤（ES 2.0）**：
  1) 收集并合并脏区，输出较小的 AABB 集合。
  2) `TileManager.planUpdates(dirtyRects)` 计算 `(tile, subRect)`。
  3) NDK/NEON 对每个 `(tile, subRect)` 执行逐行 `memcpy`，避免逐像素循环。
  4) GL 线程执行 `glTexSubImage2D`；`GL_UNPACK_ALIGNMENT=1`；设置单帧上传上限（RK3399: 8–16MB；RK3588: 16–32MB）。
  5) 渲染时低层 LOD 先显示，高层渐进替换；未就绪区使用占位/淡入。
  6) 建议灰度8上传（单通道），片元 LUT/伪彩映射以降带宽。
- **可选增强（Clipmap）**：
  - 相机大范围移动时，切换为环形条带更新，更新量仅与移动距离相关。

### 5. 关键参数与性能建议
- 瓦片尺寸：512（PoT，平衡 draw call 与更新粒度）。
- 单帧上传预算：RK3399 8–16MB；RK3588 16–32MB；超额延后到后续帧。
- 数据格式：优先 GRAY8；若资源为 YUV420 且能用外部纹理，则走 B。
- 采样参数：`GL_CLAMP_TO_EDGE`，`GL_LINEAR`；禁用 mipmap（或外部 LOD）。
- 接缝：切片生成 1px 外延 + `CLAMP_TO_EDGE`；统一浮点精度。

### 6. 测试清单（10 条，含预期）
1) 全图 4K@30fps 外部纹理：期望 UI 60fps 稳定，`updateTexImage()` 平均 <0.5ms。
2) 全图 8K 降采样至 4K 外部纹理：期望稳定显示，无明显撕裂与掉帧。
3) 局部 512×512@10Hz：期望单帧上传 <1MB，UI 帧率 ≥58fps。
4) 多脏区合并（10×128×128 相邻）：期望合并后上传量下降 ≥40%。
5) 大脏区限速（2048×1024）：期望 2–3 帧内完成，帧率 ≥55fps。
6) GRAY8+LUT：相比 RGBA 上传，带宽下降 ≈4×，画质满足需求。
7) Clipmap 平移压力：持续平移 3 屏宽，更新量与位移线性相关，无突发峰值。
8) 接缝检查：放大到像素级，瓦片边界无明显缝隙；1px 外延生效。
9) 上下文丢失恢复：前后台切换 10s，200ms 内可见区恢复，不黑屏。
10) 弱网/慢 I/O：模拟 300ms 延迟，未就绪区占位与渐进策略生效，无主线程阻塞。

### 7. 结论
- 整帧高频更新：首选外部纹理链路（B）；如必须 CPU 生成帧，优先降分辨/降频或走硬编→硬解。
- 局部高频更新：首选 Tile+LOD+脏区+子矩形上传（A），并以上传限速与 GRAY8 控制带宽；必要时引入 Clipmap（C）。
- 统一策略：根据“变化范围”动态在 A/B/C 间切换或混合（底图 B，覆盖层 A/C），实现稳定帧率与受控资源。
