## 多数据源纹理渲染（20000×20000 级）数据源对接与最佳实践（OpenGL ES 2.0）

本文聚焦三类数据源在超大纹理（最大可至 20000×20000）的高效渲染落地，结合当前工程（`TileManager`/`TexturePool`/`RegionProvider` 等）给出方案、对比、最佳选择与接入步骤。请先阅读 `docs/需求说明_AI版.md` 与 `docs/超大纹理渲染_Tile方案.md` 以统一上下文。

### 1. 数据源类型
- 1) ParcelFileDescriptor 中读到的 `byte[]`
  - 1.1 灰度图原始数据（Y8，行优先，可含行跨度 rowStride）
  - 1.2 JPEG 文件数据（压缩流）
- 2) PNG 文件（压缩流）

约束：项目为 OpenGL ES 2.0。需重点关注 `GL_MAX_TEXTURE_SIZE`（常见 4096/8192）、NPOT 限制（推荐 `GL_CLAMP_TO_EDGE`，不启用 mipmap）、移动端带宽与内存上限。

### 2. 通用 Tile 化渲染管线（复用现有实现）

```mermaid
flowchart TD
  A[输入: 地图状态/相机/有效区域] --> B[可见性裁剪]
  B --> C[LOD 选择]
  C --> D[TileManager 计算需加载/复用的 Tile]
  D --> E{LruCache 是否命中?}
  E -- 是 --> G[加入渲染批次]
  E -- 否 --> F[RegionProvider 异步提取像素]
  F --> H[TexturePool 获取纹理]
  H --> I[GL 线程 glTex(Sub)Image2D 上传]
  I --> G
  G --> J[按批次绘制]
```

- 已有关键类：
  - `TileManager`：可见瓦片计算、加载限速、局部上传（含 1px 边框外延）。
  - `TexturePool`：纹理对象复用，减少 `glGenTextures` 抖动。
  - `RegionProvider`：按 `(x,y,w,h)` 输出 `RegionBuffer{width,height,glFormat,pixelBuffer}`。
  - 已有实现示例：
    - `AlgorithmGrayscaleRegionProvider`：从整幅灰度 `ByteBuffer` 直接切片（GL_LUMINANCE）。
    - `GrayscaleRegionProviderFromBitmap`：从 `Bitmap` 提取区域并转为灰度 Y8。

### 3. 三类数据源的高效接入方式

#### 3.1 灰度原始字节流（PFD → byte[]/ByteBuffer，Y8）
- 读法：算法侧提供整幅灰度缓冲（可通过 PFD 映射/读取后得到 `ByteBuffer`）。
- Provider：`AlgorithmGrayscaleRegionProvider`（已提供）。
- 上传：`glTex(Sub)Image2D`，`glFormat = GL_LUMINANCE`，每像素 1B，极省带宽。
- 关键点：
  - 若存在行填充，使用真实 `rowStrideBytes`；按行复制目标子矩形，避免整幅拷贝。
  - 建议采用“快照”或读写分离缓冲，避免与算法并发写导致撕裂。
  - 可选择在片元着色器中完成“灰度→主题色”映射，Kotlin 端不再生成 RGBA。
- 适用：实时地图/频繁局部更新/带宽紧张场景的首选方案。

#### 3.2 JPEG（PFD 或 byte[]）
- 读法：
  - PFD：`BitmapRegionDecoder.newInstance(FileDescriptor, false)`。
  - byte[]：`BitmapRegionDecoder.newInstance(byte[], 0, len, false)`。
- Provider：实现 `RegionProvider`，对每个 Tile 使用 `BitmapRegionDecoder.decodeRegion(rect, opts)` 解码对应子矩形。
- 色彩/格式取舍：
  - 直接上传 RGBA：`glFormat = GL_RGBA`，在片元着色器做主题映射。优点：CPU 低、实现简单；缺点：带宽 4B/px。
  - CPU 转灰度上传 Y8：解码为 `ARGB_8888/RGB_565` 后逐像素转 Y8，`glFormat = GL_LUMINANCE`。优点：带宽 1B/px；缺点：CPU 有额外开销。
- 建议：
  - 默认优先“RGBA 上传 + 着色器映射”（简单稳定）。
  - 当“每帧上传量”成为瓶颈（弱带宽设备/大量区域更新）再切换为“CPU 转灰度 + LUMINANCE 上传”。
- 注意：`BitmapRegionDecoder` 支持区域解码，严禁整图一次性解码 20000×20000（会 OOM/卡顿）。

#### 3.3 PNG（文件路径/输入流）
- 读法：同 JPEG，优先 `BitmapRegionDecoder`（Android 支持对 PNG 区域解码）。
- 取舍：与 JPEG 同理（RGBA 上传 vs. CPU 转灰度上传）。
- 建议：离线资源可优先预切片离线存储（目录树/金字塔），运行时零整图解码。

### 4. 三种方式对比（高层）

- 性能与资源（相对）：
  - 灰度原始字节流（Y8）：
    - CPU：低（行拷贝）。GPU 带宽：低（1B/px）。内存峰值：低。实现复杂度：低。
  - JPEG/PNG → RGBA 上传：
    - CPU：低。GPU 带宽：中高（4B/px）。内存峰值：中。实现复杂度：中（区域解码）。
  - JPEG/PNG → CPU 转灰度 → Y8 上传：
    - CPU：中（像素遍历）。GPU 带宽：低。内存峰值：低~中。实现复杂度：中。

结论：
- 若算法可输出灰度原始缓冲：优先选择“灰度直传（Y8）”。
- 若仅有压缩图（JPEG/PNG）：默认“RGBA 上传 + 着色器映射”；带宽吃紧时切换为“CPU 转灰度 + Y8 上传”。

### 5. 20000×20000 级别的关键策略（ES 2.0）
- 必须 Tile 化：参考 `docs/超大纹理渲染_Tile方案.md`，默认 Tile 尺寸 512，必要时 256/1024 取舍。
- LOD：远景使用低分辨率，视距/像素密度驱动层级选择（后续接入）。
- 区域解码：JPEG/PNG 必须按 Tile `decodeRegion`，严禁整图解码与整图上传。
- 上传节流：`TileManager.loadPendingOnGlThread(maxCount)` 控制每帧上传预算（建议 < 4MB/帧）。
- 接缝抑制：1px 外延 + `GL_CLAMP_TO_EDGE`；片元精度使用 `mediump/highp` 合理配置。
- 纹理池与缓存：`TexturePool` 复用纹理，`LruCache` 控制常驻容量，避免抖动/峰值。

### 6. 接入步骤（最小化改动）

```mermaid
flowchart LR
  S[选择数据源] --> A{灰度原始 Y8 是否可用?}
  A -- 是 --> P1[使用 AlgorithmGrayscaleRegionProvider]
  A -- 否 --> B{JPEG/PNG?}
  B -- JPEG/PNG --> P2[RegionDecoder Provider
  (decodeRegion 按 Tile)]
  P2 --> C{带宽是否吃紧?}
  C -- 否 --> U1[RGBA 上传 + 片元映射]
  C -- 是 --> U2[CPU 转灰度 + LUMINANCE 上传]
  U1 --> T[Tile 管线渲染]
  U2 --> T
  P1 --> T
```

实施要点：
1) 统一 `RegionProvider` 接口：按 `(x,y,w,h)` 返回 `RegionBuffer(glFormat, pixelBuffer)`。
2) JPEG/PNG Provider：
   - 使用 `BitmapRegionDecoder.decodeRegion` 精确解码 Tile 对应子矩形。
   - RGBA 路线：直接将 `Bitmap` 转 `ByteBuffer`（RGBA8888）上传。
   - 灰度路线：像素遍历生成 Y8 `ByteBuffer`，上传 `GL_LUMINANCE`。
3) 灰度原始缓冲：
   - 通过 `AlgorithmGrayscaleRegionProvider` 直接按行拷贝子矩形。
4) `TileManager`：
   - 开启 1px 边框（可选）以抑制接缝。
   - 控制 `maxCount` 与 Tile 尺寸，满足帧率与带宽预算。
5) 片元映射：在 `map_fragment.glsl` 内完成“灰度→主题色”的映射，运行时可热更新主题色。

### 7. 简要伪代码（Provider 侧）

```kotlin
// 方案A：灰度原始缓冲（已实现：AlgorithmGrayscaleRegionProvider）
class AlgorithmGrayscaleRegionProvider(
    mapWidthPx: Int,
    mapHeightPx: Int,
    rowStrideBytes: Int = mapWidthPx,
    bufferSupplier: () -> ByteBuffer
) : RegionProvider { /* ... */ }

// 方案B：JPEG/PNG 区域解码（示意）
class ImageRegionProvider(
    private val makeDecoder: () -> BitmapRegionDecoder,
    private val useCpuGray: Boolean = false
) : RegionProvider {
    override fun obtainRegion(x: Int, y: Int, width: Int, height: Int): RegionBuffer? {
        val rect = Rect(x, y, x + width, y + height)
        val opts = BitmapFactory.Options().apply { inPreferredConfig = Bitmap.Config.ARGB_8888 }
        val bmp = makeDecoder().decodeRegion(rect, opts) ?: return null
        return if (!useCpuGray) {
            // RGBA 上传
            val buf = ByteBuffer.allocateDirect(width * height * 4)
            bmp.copyPixelsToBuffer(buf)
            buf.position(0)
            RegionBuffer(width, height, GLES20.GL_RGBA, buf)
        } else {
            // CPU 转灰度 → Y8 上传
            val intBuf = IntArray(width * height)
            bmp.getPixels(intBuf, 0, width, 0, 0, width, height)
            val y8 = ByteBuffer.allocateDirect(width * height)
            for (c in intBuf) {
                val r = (c shr 16) and 0xFF
                val g = (c shr 8) and 0xFF
                val b = c and 0xFF
                val y = (299 * r + 587 * g + 114 * b) / 1000
                y8.put(y.toByte())
            }
            y8.position(0)
            RegionBuffer(width, height, GLES20.GL_LUMINANCE, y8)
        }
    }
}
```

说明：以上为示意，实际实现需管理 `BitmapRegionDecoder` 复用、线程安全与生命周期；PFD/byte[]/文件路径分别构造不同的 `makeDecoder()`。

### 8. 常见问题与优化
- 大图 OOM/卡顿：严禁整图解码/上传；仅 `decodeRegion` 对应 Tile。
- 上传抖动：限制每帧上传量；必要时拆分更小 `glTexSubImage2D` 批次。
- 带宽瓶颈：优先 Y8 上传；或缩小 Tile 尺寸/引入 LOD；片元映射仍可用。
- 接缝：1px 外延 + `GL_CLAMP_TO_EDGE`；避免跨片采样。
- 颜色偏差：统一在片元做主题映射，移除 Kotlin 端像素着色差异。

### 9. 10 条验证用例（输入/期望）
1) 数据源：Y8，20000×20000；视野平移 3 屏宽；期望：仅可见 Tile 上传+绘制，FPS ≥ 55（高端）/ ≥ 45（中端）。
2) 数据源：Y8，持续 512×512 区域更新 60s；期望：上传≈0.25MB/帧，FPS ≥ 50。
3) 数据源：JPEG（PFD），缩放到全图预览；期望：按需区域解码，FPS ≥ 50；无整图解码峰值。
4) 数据源：JPEG（byte[]），连续平移+旋转；期望：无明显卡顿，上传集中在可见 Tile。
5) 数据源：PNG（文件），首次进入大范围预览；期望：`decodeRegion` 正常，内存峰值可控，无 OOM。
6) JPEG 路线对比：RGBA 上传 vs. CPU 转灰度；期望：前者 CPU 更低，后者上传带宽更低；两者均正确渲染。
7) 边框接缝验证：放大到像素级观察 Tile 边界；期望：无缝隙，采样自然。
8) 弱设备带宽压测：强制每帧更新 2×512×512；期望：通过限速仍保持 ≥ 30fps。
9) 资源丢失恢复：切后台 10s 返回；期望：可见 Tile 在 200ms 内恢复。
10) LOD 试验：缩小观测全图；期望：开启 LOD 后远景 FPS 明显高于未开启（同上传预算）。

### 10. 最佳方案总结
- 优先级：
  - 首选：灰度原始字节流（Y8）→ `GL_LUMINANCE`（带宽最省，简单稳定）。
  - 其次：JPEG/PNG 区域解码 → RGBA 上传 + 片元映射（实现简单、CPU 开销低）。
  - 若带宽受限：JPEG/PNG 区域解码 → CPU 转灰度 → `GL_LUMINANCE` 上传（以 CPU 换带宽）。
- 始终：Tile 化 + 可见优先 + 上传节流 + 1px 边框 + 纹理池复用 + LRU 缓存。
